## Severity key

- **High** — reachable unauthenticated, or defeats a control the product relies on in production.
- **Medium** — reachable by an authenticated user or a misconfiguration, with a real security or money consequence.
- **Low** — hardening, robustness, or a correctness bug with limited blast radius.
- **Info** — a stated design decision worth restating because it will surprise somebody.

## Findings

| # | Sev | Finding | Evidence | Where | Suggested direction |
|---|-----|---------|----------|-------|---------------------|
| 1 | **High** | No request body limit anywhere, and the login password has no `.max()`. An unauthenticated caller can make the server buffer an arbitrarily large body and run scrypt over it. Multipart uploads on both the staff route and the client-portal route are read fully into memory by `parseBody()` before the 25 MB check in the service runs. | Live probe: a 120 MB JSON body to `POST /api/v1/auth/login` was accepted and answered 401 after 1.6 s (the whole body was parsed and the 120 MB "password" hashed). `grep bodyLimit src` finds nothing. `MAX_PASSWORD_LENGTH` is enforced only in `setPassword`. | `src/api/router.ts` (no `bodyLimit` middleware); `src/api/handler/auth.ts:134` (`LoginBody`); `src/api/handler/filestore.ts:566` and `portalask.ts:350` (`parseBody`) | Mount Hono `bodyLimit` globally (small default) and a larger limit only on the two upload routes; add `.max(MAX_PASSWORD_LENGTH)` to `LoginBody.password`; reject on `Content-Length` before reading multipart |
| 2 | **High** | With `BIB_TRUST_PROXY=true` the rate limiter takes the **leftmost** `X-Forwarded-For` entry, which is the one the client writes. Behind a real proxy (the topology the flag exists for) every request can carry a fresh invented address, so both the auth bucket and the general bucket are bypassable. | Code: `forwarded?.split(",")[0]`. | `src/api/ratelimit.ts:113-118` | Take the rightmost entry minus the number of trusted hops, or read the address the proxy itself sets (`X-Real-IP` from a known proxy) |
| 3 | Med | Per-account login limiter counts the attempt **before** the password is verified and resets only on success. Anyone who knows an email can lock that account for an hour with ten wrong guesses. | Live probe on a fake address: attempts 1–10 → 401, attempt 11 → 429 `TOO_MANY_ATTEMPTS`, `retry in 3598s`. | `src/usecase/identity/service.ts:181-186` | Keep per-account counting but pair it with a proof-of-work or CAPTCHA step, or a shorter window with exponential backoff; surface lockouts to the firm |
| 4 | Med | A portal invite sent to an email that **already has a password** (for example a person who is staff at another firm) issues an invite link whose acceptance **overwrites that global password** and revokes every session the person holds. The first-invite path has no credential check; the resend path does (`InvitationAlreadyAccepted`). Identity is above tenant (ADR-02), so one firm's invite changes another firm's user. | Code: `invitePortalContact` never reads `credentials`; `acceptPortalInvite` calls `setPassword` → `credentials.upsert` + `sessions.revokeAllForUser`. | `src/usecase/identity/service.ts:285-310` and `485-503` | Refuse or downgrade an invite when a credential exists (send a sign-in link instead of a password-setting link), mirroring the resend path |
| 5 | Med | `BIB_ENVIRONMENT` defaults to `development`. A deployment that forgets the variable boots fail-open: dev `x-user-id` header auth accepted, `/docs` served, cookie not `Secure`, CORS falls back to the localhost app URL, `attested`/`filesystem` stubs allowed. | Code: `.default("development")`. | `src/config/config.ts:17` | Remove the default so an unset environment refuses to boot, or default to `production` |
| 6 | Med | The credit-note cap is computed with JavaScript floats: `Number(balance.invoiced) - Number(balance.credited)` compared against `Number(input.amount)`. This breaks the "only the database adds money" rule; an exact remaining credit (e.g. invoiced 100.10, credited 100.00, credit 0.10) can be refused by a rounding error, and a cap can be passed by one. | Code review. | `src/usecase/invoice/service.ts:456-462` | Compare in SQL (`numeric`) or with a decimal library; never `Number()` on an amount |
| 7 | Med | `tenancy.tenant.status = 'suspended'` has **no writer and no reader** — suspending a firm does nothing anywhere. `tenancy.user_account.status = 'disabled'` has no writer, and is checked only at login and magic-link redemption, never in `resolveSession`, so a disabled user's existing session survives up to 14 days. | `grep -rn "suspended\|disabled" src` finds only the type declarations. | `src/domain/tenancy/model.ts:23,65`; `src/usecase/identity/service.ts:547-566` | Either enforce both statuses in `resolveSession` and add the admin routes that set them, or drop the columns until there is a writer (the repo's own "registered thing with no reader" rule) |
| 8 | Med | `POST /api/v1/documents/render` trusts `partyId` from the request body. A rendered invoice or letter can be filed under any client the caller names, and because `clientVisibleByDefault("invoice")` is true it appears in **that** client's portal library. With `partyId` omitted the rendered invoice is filed under no client and is never visible to its own client. | Code review. | `src/api/handler/filestore.ts:717-733`; `src/usecase/filestore/service.ts:461-544` | Derive `partyId` from the source record (`RenderSource.describe`) and drop it from the request |
| 9 | Med | The rate limiter is in-process memory. Behind N replicas every limit is N× looser and a per-account lockout is inconsistent across pods. With `BIB_TRUST_PROXY=false` behind a load balancer every user shares the balancer's address and one 300/min bucket throttles the whole customer base. Documented as a known limit, still a production risk. | Code and comments. | `src/platform/ratelimit.ts`; `src/setup/server.ts:566` | Redis adapter behind the existing `RateLimiter` port before the second replica |
| 10 | Med | Timing oracle on `POST /api/v1/auth/magic-link`: a known address does a token generation, a row insert and the mail send inline; an unknown address returns immediately. The login route pays a dummy hash for exactly this reason; the magic-link route does not. | Live probe with the logging mailer: unknown 7–8 ms, known 14–22 ms. A real SMTP relay makes the gap hundreds of ms. | `src/usecase/identity/service.ts:212-270` | Do the send off the request (queue it), or add a constant-time floor |
| 11 | Low | The two last-administrator guards ignore role **audience**. `rolesWith('tenant:admin')` and `leavesNobodyAdmin` count a `CLIENT_PORTAL`-audience role as an administrator role, so a firm can move `tenant:admin` onto `client_contact`, pass both guards, and end with no staff role able to administer it — unrecoverable from inside the product, which is the state the guards exist to prevent. | Code review. | `src/usecase/tenancy/service.ts:781-798`; `src/usecase/config/service.ts:386-421`; `src/domain/authz/model.ts:286-293` | Filter to `audience = STAFF` in both guards |
| 12 | Low | TOCTOU on the last-administrator check: two concurrent role changes or deactivations both read the same roster and both pass, leaving zero administrators. | Code review; no lock or serialisation. | `src/usecase/tenancy/service.ts:781` | Take a per-tenant advisory lock or check inside the UPDATE transaction |

## What held up

- Tenant wall: RLS with a policy on every tenant-scoped table, verified against the catalogue; composite `(id, tenant_id)` foreign keys; `withTenant`/`withIdentity`/`withPortal` are the only paths to tenant data; the boot check refuses a bypassing role.
- Gate 4 restrictive policies on every portal-readable table, written in terms of `crm.portal_sees()`; an empty grant list reaches the database as an empty list.
- Every portal handler refuses a `STAFF` session rather than answering empty.
- Passwords: scrypt (N=2¹⁵, r=8) with a concurrency gate; dummy-hash on the unknown-email login path; tokens are 256-bit CSPRNG stored as SHA-256 digests; the internal key is compared in constant time and carries per-client capabilities.
- CORS is an exact-origin allowlist; a preflight from an unknown origin gets no `Access-Control-Allow-Origin`.
- Gates 2 and 3 are deny-by-default and structurally tested (`tests/api/auth-coverage.test.ts`).
- The ledger is append-only at the grant level, checked at boot, and refuses PII keys and unknown verbs before writing.
- Fee-axis redaction is applied consistently on proposals, invoices, payments, credit notes, balances and the dashboard.
- No dynamic SQL identifiers from user input; all `db.unsafe` uses are constant column lists or the migration runner.

## Side effects of this audit

- Finding 3 was proven against the fake address `lockout-probe@nowhere.invalid`; that lock lives in the dev server's memory and clears on restart. No real account was touched by this session.
- Finding 1 was proven with a single 120 MB request to the local API; nothing was stored.
- No rows were written to the local database by this session.
