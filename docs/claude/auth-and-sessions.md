# Authentication, sessions and passwords

Scope: the two guarded surfaces (`/internal/*`, `/api/v1/*`), public routes, audience gate 2, the `PrincipalResolver` and server-side sessions, and passwords (0082). Mail transport for sign-in links is `notifications-and-mail.md`; CORS and rate limits are `security-and-operations.md`.

## Authentication: two surfaces, both guarded by PREFIX

Authentication is **middleware on a path prefix** (`api/guards.ts`), never a check a handler remembers (three routes once shipped unauthenticated because the check lived in each file).

- **`/internal/*`** is the platform's provisioning API (create tenant, grant membership, register user, set password). No end user behind it, so **each caller has its own key** (`BIB_INTERNAL_KEYS`) carrying only the capabilities it needs, compared in constant time (one key opening every route was an escalation path: create a user, make them partner, set their password, sign in as them). Capabilities live in `ROUTE_CAPABILITIES` (`api/capabilities.ts`), **denied by default**: a route with no entry is refused to every key. `credential.set` grants a login as somebody, so boot refuses it sharing a key with anything else in a production-like environment. Services record these writes as the **system** actor with the caller's name in the payload.
- **`/api/v1/*`** requires a session. The only exceptions are routes that exist to *obtain* one (and the proposal share-link routes, `proposals-letters-and-engagements.md`), listed by exact path in `PUBLIC_PATHS`. `tests/api/auth-coverage.test.ts` pins the list, so a new entry is argued for; a public route needs an argument written beside it.
- **Audience (gate 2) is denied by default.** A `CLIENT_PORTAL` session reaches only `PORTAL_PATHS`; everything else is the STAFF workspace and answers 403. (B2B2C: an authenticated, in-tenant session says nothing about which of staff / client the caller is; the reverse default would let a client contact list the firm's whole book.) Portal routes join `PORTAL_PATHS` **and** need record scope (gate 4).
- **A portal session is TOLD it may do nothing, whatever role it holds.** Nothing refuses a staff role on a `CLIENT_PORTAL` membership (gate 2 runs before gate 3 and refuses every staff route), but `/auth/me` promises "a screen offers only what will work", so `permissionsOf` returns `[]` for a portal session. That is arithmetic, not policy; `tests/api/portal-permissions.test.ts` reads both tables and goes red the day a portal route needs a permission. The real fix, a role declaring its audience, costs a migration.
- Handlers read the principal from context (`c.get("principal")`) and call `scopeOf()` (`api/scope.ts`) for a tenant: 401 "not signed in" and 403 "signed in, but no org chosen" are different answers.
- `auth-coverage.test.ts` enumerates **every route the Hono instance registered** (not the OpenAPI spec, which is blind to plain `app.get()` routes like `/health`, `/docs`) and fails if any route outside the allowlists answers anything but 401 anonymously. A new route is covered automatically.

**Sessions.** A request becomes a `Principal` through the **`PrincipalResolver`** (`api/principal.ts`): a session cookie (or `Authorization: Bearer`) resolved against `tenancy.session`. Sessions are server-side because they must be **revocable** (a dismissed member loses access that afternoon). `resolveSession` **re-checks the membership on EVERY request** (checking only at login and org-switch left a deactivated member working up to a fortnight). The token is only a SHA-256 digest at rest and only leaves in an httpOnly cookie, never a response body. `Principal.tenantId` and `audience` are **null until an org is chosen**: a multi-membership user calls `POST /api/v1/auth/switch-tenant`; nothing guesses. Dead sessions and sign-in links are among the few rows `bib_app` may DELETE (0075).

**Honest registry.** The dev `x-user-id` resolver, the logging mailer, the attested e-sign signer and the filesystem blob store are stubs gated on config; `validateServer` refuses a production-like boot with any, and `tests/config/boot-gates.test.ts` proves each refusal (a gate that stops refusing breaks nothing and is silent). Do not add another without the same treatment. The mailer has a real counterpart (`smtp`); the `log` stub and its gate stay.

## Passwords: setting, changing, forgetting (0082)

Until 0082 nothing in the product could write a credential except `PUT /internal/v1/users/{userId}/password` (platform key). Two holes: a **CLIENT CONTACT** sets a password once on the `invite` link and it is spent (`resendPortalInvite` refuses once a credential exists by design: re-issuing would be the firm resetting its own client's password); a **COLLEAGUE** usually has no password (`welcomeStaff` hands over a session only). Three routes; the split is the design.

- **`POST /api/v1/auth/password-reset` is `requestMagicLink` line for line**: same silence, per-address budget, `MAGIC_LINK_FLOOR_MS` constant-time floor, swallowed send. Unknown address, deactivated account, spent budget and dead relay all answer 202 in the same time. It does **not** check whether a password exists (that would be an enumeration oracle, "which staff have passwords?", and setting a FIRST one through it is the answer for staff).
- **`reset` is a FOURTH magic-link purpose.** `login` and `welcome` open a session (`SESSION_OPENING_PURPOSES`); `reset` must not (the holder proved only they read a mailbox; a reset redeemed at sign-in would hand out a session and leave the old password). `invite` is wrong at both ends (7-day life; `resendPortalInvite` refuses once a credential exists). `PASSWORD_RESET_TTL_MINUTES` is **30** (sign-in link 15) because the form needs a person to CHOOSE something.
- **Issuing one SPENDS every live one** (`consumeUnusedFor`); otherwise an impatient reader leaves three live setters in a mailbox.
- **`POST /api/v1/auth/password` requires the CURRENT password; the session does not stand in for it. Do not weaken.** A stolen session must not be able to MINT a password (sessions are server-side so revocation works; a password minted from one would survive every revocation). **An account with no password is refused here** (`NoPasswordSet`) and sets its first through the emailed link.
- **Re-using the old password is deliberately asymmetric:** `changePassword` refuses (`PasswordUnchanged`; a green tick that changed nothing is worse); `resetPassword` accepts (the holder does not know the old value).
- **Both paths revoke every session and hand back a new one.** Reset: the commonest reason is suspicion somebody is in. Change: `reopenSession` opens a fresh session pointed at the firm they were acting as, re-checking membership and firm standing; the token rotates.
- **The reset letter is a FIFTH method on `Mailer`** (one paragraph differs: "if you did not ask, nothing has happened" is false of a link that REPLACES a credential; the password still works while the link is left alone). It names no firm (account is GLOBAL, ADR-02).
- **A colleague's FIRST password is chosen on the welcome link (audit 2026-10-03, CA#38).** With no credential the welcome button is "Choose your password" → `/auth/welcome`, whose form calls `POST /auth/magic-link/redeem` WITH a `password` (`redeemWelcome`: welcome purpose only, no existing password only, length checked before the link is spent, set + sign in in one call). "Skip" is the same route without one. An account that already has a password (global identity; a second firm's welcome) goes to `/auth/magic-link`, and a password sent for it is refused `PASSWORD_ALREADY_SET` (409) WITHOUT spending the link. No new public route. The letter names the colleague who added them (CA#50) and goes out under the firm's name (CA#40, `fromName`).
- A wrong CURRENT password on `POST /auth/password` is `CURRENT_PASSWORD_INCORRECT` (400, "That is not your current password.") not 401 (F26: the form has no email box; a 401 reads as signed out).
- **`/auth/me` carries `hasPassword`** so the account screen offers the form that will work.
