# Clients, parties, leads and the client import

Scope: parties are permanent (archive, not delete), identifiers (phone E.164, PAN/GSTIN), correcting master data (0315), the account team (Key Manager / SPOC, G3.2), leads and assignment, input-validation rules from the 2026-10-03 audit, client-company registration (Q076), and the client import (T6.12). Deleting a mistaken lead/draft is `ledger-and-records.md`; the firm's own companies are `document-content-and-issuers.md`; "today" in `?asOf=` is `dates-and-timezones.md`.

## Parties are permanent (G0.3)

**There is no `deleted_at` in `core` and there never will be.** A client created by mistake is ARCHIVED: `core.party.archived_at` (0035) means "keep this out of pickers and lists", nothing more. A real company's lifecycle is answered by the ledger and `core.legal_entity.status`. Reason in one sentence: a signed engagement letter's counterparty must always resolve.

- The LIST hides archived parties and takes a flag to include them; reading ONE party by id ALWAYS returns it. That asymmetry is the design (one column on one table, not `deleted_at` behind a filter every read must remember).
- **Archiving is refused BY A TRIGGER** while anything live points at the party (`core.refuse_archive_with_references()`; 0314 rewrote it): an open lead, a draft or sent proposal/letter (and a proposal line's / letter line's entity), a `pending_advance` / `active` / `paused` engagement. The refusal names them. Leads, proposals and letters DELETED as a mistake (0086) and their lines do not count. A trigger because an import or agent walks past a service; it costs nothing on ordinary writes (`BEFORE UPDATE OF archived_at` with a `WHEN` on the NULL → NOT NULL transition; a rename fires nothing). **Read it as "you cannot put away a client you are still working with"**, checked at the moment of archiving. For a client who leaves: End each engagement, then Archive (`proposals-letters-and-engagements.md`).
- **An archived client gains NO new reference (0305, decided 2026-09-25).** Lead capture resolved a party by PAN without consulting `archived_at`, and a proposal/letter could be drafted against one by id. **Refused, never quietly restored** (putting a client away was a person's decision): restoring is its own act (`POST /parties/{id}/unarchive`, the client page's Restore). Services refuse first, BY NAME, pointing at the restore: `PARTY_ARCHIVED` (409) in lead, proposal and engagement families (capture, drafting a proposal/letter, adding a line whose company is archived, `draftFromQuote` before any letter exists so no reference number is spent). The wall: `core.refuse_reference_to_archived_party()`, BEFORE INSERT / UPDATE-OF trigger on six commercial references (lead, proposal, proposal line entity, letter, letter line entity, both of the engagement's), firing only when the reference is new or changed, naming the party by id never name (it reaches a server log). NOT covered, deliberately: the firm's own issuing entity, a letter's care-of person, delivery tables (produced from an engagement that cannot exist for an archived party). The import already refused an archived company ("Unarchive it first"). Invoices follow too (`document-content-and-issuers.md`).

## Identifiers: phone, PAN, GSTIN (2026-09-30)

- `normalizeIdentifier("phone", value, country?)` returns E.164 (`+919820012345`); `isValidIdentifier` refuses anything else (`domain/party/phone.ts`, stdlib only; the screen uses it). Two strengths: every phone must be E.164 (a "+", a code not starting with 0, 7-15 digits), and the firm's countries must have the right length and a leading digit that country uses (IN 10, AE 9 mobile or 8 landline, SG 8, US/CA 10, GB 9 or 10).
- **A number with no "+" is completed only when the caller says the country**; nobody guesses: the party route uses the identifier's `jurisdiction`, lead capture the lead's country, the client import the company the people row is for (carried to confirm as `report.peoplePhones`).
- **Lead capture normalises and checks every identifier BEFORE the dedup lookup and any write** (a bad one used to be refused only after the prospect existed).
- **GSTIN is held to its structure** (`27ABCDE1234F1Z5`: state code, PAN, entity number, a fixed Z, a check character; the check character's arithmetic is not tested). Refusal `INVALID_IDENTIFIER` says what a good value looks like. Phones stored before this are not rewritten: a lookup of the old bare form will not match the E.164 form.
- **Duplicate identifiers name the holder** ("The email x is already recorded on Acme…"), never "for this tenant". The duplicate check reads only OPEN identifiers.

## Correcting a client's master data (V2.5, 0315)

`PATCH /parties/{id}` (display name, trade name, industry, website; absent = unchanged, blank = cleared), `PATCH /parties/{id}/legal-entity` (country, kind, `financialYearEnd`), `POST /parties/{id}/identifiers/{identifierId}/end` (a GSTIN cancelled on a day) and `.../void` (entered by mistake: `voided_at`, kept, shown, FINAL by trigger 55000), all `party:write`; `PATCH /tenancy/me` edits your OWN display name only (the account is global, so a firm renaming a colleague would rename them at every firm; no permission, like your own password). **The duplicate check reads only OPEN identifiers**, so voiding the wrong PAN frees it for the right client. Every event names the FIELDS changed, never values (`party.updated`, `legal_entity.corrected`, `party_identifier.ended` / `.voided`, `user.renamed`). A rename reaches every list and NEW render; a signed letter is frozen and a FILED PDF is stored bytes, but an invoice PDF rendered on demand reads the client's CURRENT name (render-source joins `core.party.display_name`); snapshotting the billed name at Issue is a follow-up, not done (0334's `printed_parties` freezes it once issued).

## Input rules from the 2026-10-03 audit (UX cluster)

- **A country is one of the 249 ISO 3166-1 codes** (`domain/country.ts`). `isJurisdiction` (lead, territory rules, proposal/letter lines, firm companies, documents) requires one, as do filing rules, a client's registration and the import's Country / Where columns. A retired or reserved code (DD, UK, SU, YU…) is refused with `countryCodeProblem()` naming what was meant ("For Germany, use DE"): a dead code is silently matched by no rule. Config bodies' `jurisdictions` arrays are NOT checked yet (published bodies are frozen; screens offer real codes).
- **A refused amount says what is wrong** (`amountProblem()` in `domain/money`): "The amount cannot be 0.", "The tax rate cannot be more than 100%." Wire rule (decimal strings) unchanged.
- **A lead's contact person** (`CaptureLeadInput.contact`, CA#20): with one named on a company prospect, email and phone go on a PERSON linked to the company in a contact's role; the company keeps PAN and GSTIN. Dedup follows the person to the company, and a detail an older capture put on the company still matches the company.
- **A relationship must be able to be true** (`relationshipFits`): nobody is a director or shareholder OF a person; only a person is an employee or signatory; a parent and subsidiary are both companies. A company as a director is allowed (some countries allow it).
- The shipped rule pack's notes no longer speak as one firm; the pack KEY (`in-firm-sheet@2026.08`) is unchanged (part of the seeding conflict key); the frontend prints it as words.

## A client company's registration is required (Q076, 0350, 2026-10-05)

`POST /parties/organizations` (Clients screen) is `PartyService.createClientCompany`: **country and type required, year end required outside India, India fixed at `03-31`** (`yearEndProblem` / `yearEndFor`), all three rows in one transaction. `createOrganization` (no registration) stays for a lead's prospect and an import's group umbrella. Registering and correcting follow the same rule. A proposal or letter (draft, copy, from a quote) or a line for an ORGANIZATION with no registration is refused, `COMPANY_NOT_REGISTERED` (409), in `draftProposal`/`draftLetter` (a person is never asked): a lead's prospect must be registered before it is quoted. Import: abroad with no year end is a row error. Setup's `client_details` line names every client company QUOTED OR ENGAGED missing `country`/`company_type`, or abroad `year_end` (`firm-setup-and-structure.md`). Nothing is backfilled.

## Leads and assignment (T2.1, T2.1b)

- **A lead is a party.** The pipeline keeps no copy of a prospect: capture resolves a party by identifier FIRST (phone + PAN + email, normalised) and `crm.lead` holds only the opportunity (source, stage, owner). At most one OPEN lead per party (partial unique index), so a duplicate capture *appends*. Capture goes through `PartyService` behind the lead use case's own `ProspectDirectory` port (same validation and `party.created` events). A lead has no timeline table: its history is the ledger.
- **Assignment is territory first, rotation second.** `FirstMatchAssignment` in `setup/` takes an ordered array; the ORDER is the firm's precedence (a third rule is a line there, not a branch). `crm.territory_rule` says whose desk covers a country, keyed on `crm.lead.jurisdiction` (nullable: often unknown at capture). **No wildcard rule**: the rotation is the fallback. A rule never overrules a person; a rule whose desk was revoked DECLINES (a join inside the strategy's own statement; no FK can express "active").
- `AssignmentStrategy.assign` returns `{ lead, policy }` because which rule chose is a fact about the LEAD: `lead.captured`'s `ownerAssignedBy` is evidence about whether the rotation works. The API runs the strategy only when no owner is SENT. New-lead notifications: `notifications-and-mail.md` (Q066).
- Deleting a mistaken lead: `ledger-and-records.md`.

## Who owns a client: the Key Manager and the SPOCs (G3.2)

`crm.client_assignment` (0049): who at the firm looks after a client, effective-dated. **Key Manager** = one at a time, owns the relationship. **SPOC** = day-to-day contact for one Dept or delivery team; the firm's practice is one per Dept ("each client will defacto have two SPOC, one from TRC and one from FRC"); a client buying RAA work has three, hence a row per assignment. In `crm`, not `tenancy`: the firm describing a RELATIONSHIP with a client.

- **`axis_id`, not `module_id`**: 0043 made Depts and delivery teams one list; pinning to `dept` leaves a teams-only firm nowhere (and avoids settling the Dept-vs-team question in DDL). Enforced structurally: a SPOC has an axis, a Key Manager never does.
- **A DEPT MAY HAVE MORE THAN ONE SPOC (decision, Shrestha 2026-08-30)**: leave cover, a joint SPOC on a group, a parallel handover. No "one per axis" constraint; "who was SPOC in March" may be a LIST and every reader takes one. `ownership.integration.test.ts` tests the ABSENCE (dropping a constraint later is one line; adding one fails against the overlap already recorded).
- **Two EXCLUSION constraints, not a partial unique index** (`btree_gist` + `daterange(valid_from, valid_to, '[)')`): one Key Manager at a time per client; no duplicate (same person, role, axis, overlapping). An index over OPEN rows constrains only today; two CLOSED rows overlapping in March would give "who was KM in March" two names.
- **Half-open `[valid_from, valid_to)`**, `valid_to` the FIRST DAY NOT IN FORCE (like `party_relationship`, `party_identifier`, `isInForceOn`; the demo's inclusive bound would show two SPOCs on every changeover day). **A handover closes the old row at D and opens the new at D in ONE transaction**, never an `UPDATE` of `user_id`.
- `GET /api/v1/my-clients` takes `asOf` (the browser's local day); `CURRENT_DATE` appears nowhere in this module's SQL; defaults are the firm's day. The `asOf`-on-writes rule (`isCallersToday`, `NOT_CALLERS_TODAY`; `invoice` and `lead` follow it since 2026-09-25) is in `dates-and-timezones.md`.
- `party:read` to see an account team, `party:write` to change one (not `tenant:admin`); naming a Key Manager grants nobody anything. The assign form's pickers read `/tenancy/colleagues` and `/tenancy/axes` (ACTIVE Depts and teams, both `party:read`, since 2026-09-25); the full structure, retired rows and the split axis stay `tenant:admin`.

## Loading a firm's existing book: the client import (T6.12)

`usecase/clientimport` + `crm.client_import` (**0079, the last number in (B)'s old range**). Every firm arrives as spreadsheets; a half-true book is worse than none (the calendar is empty for exactly the clients everyone assumes are in).

- **TWO ACTS, TWO REQUESTS, ONE STAGED ROW.** `POST /api/v1/client-imports` (multipart: clients sheet, optional people and engagements sheets, `.csv` or `.xlsx` via the dependency-free reader in `infrastructure/sheet/`) parses, checks every row against ONE snapshot of what the firm has, stores rows + report, writes nothing else. `POST …/confirm` re-checks (records may have moved) then walks the plan. The staged row holds the sheet (JSON limit 256 KB; the confirmer must confirm what they READ).
- **Same doors as the screens, enforced by what the module lacks**: its writer ports are `PartyService`, `ClientAssignmentService`, `EngagementService` (narrowed structurally); the only table it writes is its own. So an imported client is a client (`party.created`, `legal_entity.registered`, `client_assignment.created`, `engagement_letter.signed`, `contract.activated`) and the scheduler/calendar act as for a typed one. Its own two verbs carry COUNTS only.
- **A MIGRATED ENGAGEMENT IS A REAL SIGNED LETTER** (`crm.engagement` cannot exist without a letter line, 0017). One letter per client per currency, dated from its earliest engagement, `advanceRequired: false`, clauses by `clausesFor` (apply to the country, name no other country's law), sent, then signed with the sheet's Signatory (or a sentence saying the name is on the paper) and the paper letter's whereabouts in the reference. **The signature day is TODAY, never backdated** (`signedOn` in `demo-seed.sh` was always silently dropped by zod); `issuedOn` and `effectiveFrom` backdate, and `effectiveFrom` is what the calendar reaches back from. `send(…, { migrated: true })` never raises a DocuSign envelope.
- **Stated in the report:** a letter's country needs a clause in the firm's library or every line for it is BLOCKING; a firm with no `compliance_policy` floor and engagements older than 90 days gets a WARNING naming the count (filings already made in Excel would show MISSED; walked, and it happened).
- **BLOCKING is the sheet's fault; a warning is worth a look.** A row already on file (registration number first, name second) is SKIPPED, never updated. **Confirm is NOT one transaction**: each service call commits alone, a row failing halfway is reported with what it got done; the second run is boring by design.
- **The account team goes on the GROUP's row** (a group's companies are billed on the group's letter and routed by the group's SPOCs; a SPOC typed on a company's row is recorded there and routes nothing; the template says so, the validator does not guess).
- `tenant:admin` on every route (one confirm creates parties, letters and assignments; the report names the roster by email).
- **An Excel date is a NUMBER and only its style says so (2026-09-30).** The first real sheet on QA was refused on every date (`2019/11/12` stored as `43781`; the reader ignored `xl/styles.xml`). It now reads each cell's `s` → `cellXfs` → `numFmtId` (built-in, or custom `formatCode` with a day/year token once literals and `[...]` are stripped), writes a date-formatted number as `YYYY-MM-DD`, honours `date1904`, refuses Lotus's 29 Feb 1900; a boolean cell becomes `TRUE`/`FALSE`. Financial Year End keeps month and day of a whole date (`monthDayOf`: Excel adds the current year to "31/03"). A NAME typed where a login email belongs is refused, naming the email it belongs to or every colleague sharing it (picking one of two Ashishes is a guess about who owns a client). Bounds on the reader: `security-and-operations.md`.
