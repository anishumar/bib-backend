# Escalation ladder, chaser, freeze and nudge

Scope: the three sweeps that SAY something and never act: the inward escalation ladder (T4.5, 0058), the outward chaser (T4.4, 0065) with the client freeze, and the proactive nudge (T6.7, 0067). The client-facing reads of their rows are in `client-portal.md`; missed-deadline decisions are in `compliance-calendar.md`.

## The escalation ladder: the sweep that tells somebody (T4.5)

`delivery.escalation_notice` (0058) plus `escalation`, the registry's TENTH kind. It watches three dates the product already holds and raises a notice; it changes nothing else, ever.

- **0052 SAID THIS OUT LOUD AND NOTHING EVER FIRED** ("the escalation ladder fires on the internal target rather than the statutory"). The morning it was built the live DB held **7 work items overdue, 5 on nobody's desk**, and **2 filings past `internal_target_on` with the statutory date still ahead**. If you find a comment describing a mechanism, check the mechanism exists (the third such).
- **IT IS NOT AN AGENT** (deviation recorded). A9 sits in Phase 4 and deliberately does not run through T2.8's runtime: `AgentRuntime.run` is `{ tenantId, jobId, stepKey }`, step-scoped, and this has neither a job nor a step ("no human trigger" is its own board line). It produces no proposal, so no confidence for a tier to govern; forcing it through would invent a fake job and a confidence of **1.0 for arithmetic over two dates**, which would sit in the accuracy record making real agents look better than they are. The shape it matches is `usecase/dunning`.
- **IT NEVER ACTS, structurally**: `EscalationService` holds five read ports and one write; there is no seam through which a task could be reassigned, a filing moved or a client contacted.
- **THREE WATCHES, NO NEW DATE INVENTED:** `work_item_due` (the SLA T3.1 snapshotted), `work_item_unassigned` (counts from `created_at`; an item the router refused to guess an owner for has no other clock), `obligation_target` (T3.2's `internal_target_on`). No fourth watch may need an invented deadline.
- **NOTHING IS SEEDED.** No published ladder = nobody escalated (same direction as `dunning`, `confidence_tier`; a threshold this product invented teaches everyone to ignore the one queue whose value is being believed). `GET /api/v1/escalations` returns **`ladderPublished`**, since an empty queue at a firm with no ladder and one where everything is on time are the same picture.
- **Ascending is per WATCH, not across the array** (differs from dunning's validator): three independent ladders sharing an entry.
- **WHO IT REACHES: `assignee` · `manager` · `grade_at_least`, and all three can reach NOBODY.** The manager hop resolves TODAY through `membership.reports_to_user_id` (**G3.4 is not a blocker**: it links a login to a PARTY, a different question). `grade_at_least` is deliberately NOT resolved to a person (a notice routed to one partner dies while they are on leave): `min_grade_rank` is stored and the reader's own rank matches. When nobody can be named the notice still fires, with a sentence saying which of the three reasons (T3.1's `assignment_note` decision); the first real sweep raised 14 rungs, **7 reached nobody**: the rows a partner has to act on.
- **THE TABLE EXISTS BECAUSE THE SWEEP'S `WHERE` CANNOT READ THE LEDGER** (T3.3's `resolved_at` lesson): without a row the same rung fires every morning. Idempotence = two partial unique indexes + `ON CONFLICT DO NOTHING`; the event is written only when a row was created (`dunning`'s arrangement).
- **NO `cleared_at`.** A notice about a task is live exactly while the task is not terminal; about unassigned work exactly while nobody holds it; the queue reads a JOIN (a restating column can disagree). Proven by running it: cancelling a task dropped its three notices, reopening brought them back, nothing re-raised.
- **THE BOUNDARY WITH T3.3 IS WHY THESE ARE TWO SWEEPS.** `obligation_target` fires between the firm's T-X and the statutory date and **stops when the statutory date passes** (from there it is in the partner's decision queue; two systems shouting about one filing gets both ignored). `obligation.escalated` is its own verb beside `obligation.missed`.
- **Reading is `party:read`; there is NO write route** (no acknowledge/dismiss/snooze: a notice ends when the WORK ends; a control that emptied the queue would make it decoration). The unfiltered queue is the default (T3.3's decision); `?mine=true` is resolved from the caller's own membership, never the wire.
- **Found by running it: a read model with a name and no email.** 14 notices, three addressed to a partner by name, and the queue rendered a blank: `tenancy.user_account.display_name` is nullable and empty at seeded firms, so `raisedToName: string | null` collapsed "told somebody whose name we do not hold" into "told nobody". **The email is the discriminator, not the id**: both people on the row are `{ userId, displayName, email }` now (the shape `EventRecord.actor` has); the sixth read model caught, the first missing the email rather than the name.

## The chaser: the same ladder aimed OUTWARD (T4.4)

`usecase/chaser` + 0065. T6.6 built the row saying WE ARE WAITING ON YOU and nothing sent a second one; this is the only board task that reduces the firm's own chasing hours.

- **T4.5's MECHANISM, NOT T4.5's TABLE:** rungs keyed by name, a day threshold copied onto the row when it fires, at-least-once, nothing set by default. But `escalation_notice` records a COLLEAGUE told; this records a CLIENT reminded (different reader, target, stop; sharing would put "and not the outward ones" in every escalation query forever). **ITS OWN CONFIG KIND** (an `EscalationRung` carries `watch`, `notify`, `minGradeRank`; a chase has one subject, an open `client_ask`, and one recipient; reuse would mean three always-unread fields and a validator that cannot refuse a nonsense rung).
- **IT SENDS NOTHING: the board's hard limit met structurally.** Transport is P10 (Phase 7): a chase RAISES a reminder and the client's action centre shows it. No mailer is injected (an honest logging stub would put a line in a log saying a client was emailed, the same lie as a `scan()` returning clean). `ChaserService`'s dependency list is asserted in a test.
- **IT CHASES OPEN ASKS ONLY** (reminding someone about something they already sent is what a human chaser gets wrong every week); it skips an ask whose task the firm marked invisible to the client.
- **AT-LEAST-ONCE AND EVIDENCE-GRADE:** `client_ask_chase_once` makes a redelivery unwritable; the event is emitted only for created rows; the table is APPEND-ONLY BY GRANT ("we reminded you four times" is what a firm says when a filing goes late). The actor is the SYSTEM, honestly, which is why there is no "chase now" route.

### Escalation freeze

The acceptance line said "stops on escalation freeze" and the product had no freeze. Shape is a CLIENT FACT (Shrestha, 2026-09-01):

- **On the CLIENT, effective-dated** (a dispute is with a client, not one task; a per-ask snooze would go silent again when an eighth ask is raised). **It stops the OUTWARD ladder only**; T4.5 keeps telling the firm its work is late (a dispute is the worst moment to go blind).
- **A reason is required** (asked months later by somebody who did not set it). On the ROW, never in the ledger (§3.4, the split `obligation.resolved` makes).
- Half-open `[valid_from, valid_to)`. Lifting defaults to TODAY (0061's decision applied again: resume means the next sweep chases). Setting a freeze in force on no day is refused by the service while lifting produces exactly that shape twenty seconds later (the DB allows the shape; the service allows only the act).
- **No portal policy on `crm.client_freeze`, deliberately** (gate 2 contains it; whether a client may see they are frozen is a firm's question; a portal route on that table needs its own migration line first).

### What building it found

- **A CONSTRAINT THAT WAS WRONG, only the integration test could say.** `crm.client_freeze` first carried `client_ask`'s both-or-neither pairing on `(valid_to, lifted_by)`, refusing a freeze that ENDS on a known day ("frozen until the 30th, while in mediation"). The true invariant runs one way: a LIFTER with no end date is impossible. 0065 was uncommitted and local, so corrected in place and proven by a full down/up round trip rather than an 0066.
- **The T-3 half of the board's line is not built on purpose** (a filing approaching its date asks the client for nothing; "your GSTR-3B is due in 3 days" is a NUDGE). There is no ladder screen: it is reachable through the generic config API.

## The proactive nudge: the same ladder pointed the other way (T6.7)

`usecase/nudge` + 0067. T4.4's board line "T-3 daily, D+3/7/15": only the D+ half was built.

- **NOT THE CHASER WITH A MINUS SIGN.** A chase is about an open `client_ask` (the firm wants something back; the count is evidence). A nudge is about an `obligation_instance`, wants nothing back, names a date the LAW set. The chase counts FORWARD from when the firm asked (`afterDays`, ASCENDING); the nudge counts BACKWARD from a statutory date (`beforeDays`, strictly DESCENDING: 7, 3, 1). Its own kind (bending the chaser's would need a sign convention on a field called "after").
- **THE WALL COLUMN IS `entity_party_id`, NOT THE CLIENT** (0053): a contact granted Cobalt Foods is nudged about Cobalt Foods' filings and not its subsidiary's even though the subsidiary's TASK is on their page. Reaching them would join `crm.engagement`, the nullable derivation refused three times. A contact who needs both gets two grants.
- **THE FREEZE DOES NOT STOP IT.** The date is the LAW's, not the firm's (going quiet about a statutory deadline because a fee is disputed exposes the client to a penalty and the firm to a claim for knowing and saying nothing), and structurally it cannot reach (freeze keyed on `client_party_id`, obligation carries `entity_party_id`). A firm wanting one needs its own effective-dated row on the ENTITY with its own migration and argument.
- **Nothing by default, at-least-once, append-only by grant, no transport.** `tests/nudge/service.test.ts` asserts the dependency list STRUCTURALLY, including the ABSENCE of a freeze port (one that took freezes and ignored them is worse than none).
- **It never offers a filing already discharged or PAST its date.** `filed_on IS NULL`, not a terminal-state test (0052 seeds two terminal states and `resolved` ends a MISSED deadline: calling it "coming up" is 0054's false statement from the other side). `days_until >= 0` is a CHECK and the query's predicate ("due in -5 days" is not a sentence; a past filing is a missed deadline with its own screen).

## What the chaser's rows waited for, and what T6.7 decided about them

`delivery.client_ask_chase` (0065) had a WRITER, a portal policy and a ledger event, and **nothing rendered it** (the sixth registered thing found in that state, after `membership.revoked`, `obligation.filed`, the ladder's comment, `is_client_visible`, `files.document.party_id`). 0065's comment claimed the client's action centre showed "how many times it has been reminded and when"; false when written. 0065 is immutable, so only half ships and the other half is a decision.

- **The FIRM sees every rung** (`AskRecord.chases`: key, threshold that fired, day): a colleague who cannot see the sweep chased three times will chase a fourth by hand. **The CLIENT gets a DATE and no tally** (`PortalAskRow.lastRemindedAt`, a `max()`): "we have reminded you 4 times" is an accusation printed on their own page ("9 times" within a fortnight on a daily rung); a date tells them whether they missed a message (Shrestha, 2026-09-01). The nudge's reader is the same: `PortalFilingRow.lastNudgedAt`, a date, not a count.
- **What building and walking T6.7 found:**
  - **The narrowing hid the firm's own papers from the firm** (detail in `client-portal.md`): caught by `tests/portal/library.integration.test.ts`'s first assertion, "a STAFF session is untouched", the first check whenever a restrictive policy lands.
  - **A client's own upload became unreadable to them**: `PostgresPortalAskRepository` inserted the document without the new flag (default FALSE); it leaked nothing, it made the INSERT fail the policy's `WITH CHECK` (a portal session cannot write a row it could not read): what a client sends, a client sees. The firm's default-by-kind mapping must not apply there (the kind was chosen by the firm; a file filed as `working_paper` would vanish from the sender).
  - **`subject_kind = 'work_item'` had no firm-side reader** (0063 added it; `/work-items/[workItemId]` had no `<Documents>` panel): added, and it is where the visibility switch lives.
  - **A down migration failed halfway** (0067's first down dropped its table and key and only then tried to narrow `entry_kind_check`, which a DB holding a published `nudge` entry refuses; the refusal lands AFTER the drops, leaving the constraint gone). It now ADDs the narrow constraint under a temporary name FIRST, then swaps. `npm run migrate` wraps each file in a transaction and would have rolled back: **a down is run by hand, against a database somebody is trying to rescue.**
  - **`worker:once` claimed to run everything and did not** ("ALL FIVE sweeps"; T4.4 registered the chaser on the worker's queue without adding it here). There is no count in that comment any more; the list is the list.
  - **The sweep's "nothing to do" line told a partner something false** ("a firm that has published no chaser ladder chases nobody" on a run where the demo had just published one). Two causes; a line that picks one is worse than one that names both.
