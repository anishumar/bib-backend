# Work items, maker-checker, review and the owner rule

Scope: tasks (`delivery.work_item`, T3.1) and the firm's own vocabulary; routing (the owner rule, 0311, turn-taking SPOCs, the catch-up); the review loop and notes (0330); who may check somebody else's work (T2.9, `verification_policy`, Q069); the Send routing warning. Steps, sub-steps and the engine are `delivery-engine-and-workflow.md`.

## Work items: the row on somebody's desk (T3.1)

`delivery.work_item` + `checklist_item` + `work_item_dependency` + `work_item_approval` (0051), over `work_item_state` + `work_item_priority` (0050).

- **It is NOT `job_step`.** A JOB is HOW work gets done (template, steps, agent; the ENGINE's states, identical at every firm). A WORK ITEM is WHAT is owed and WHOSE (the FIRM's own state words). Merged, ad hoc work ("prepare the board minutes") has no home and a firm renames the engine's mechanics to get its board to read. `work_item.job_id` is nullable both ways (many items on one merged job; an item with no job).
- **MEANING IS A FLAG; NAMES ARE THE FIRM'S. Nothing compares a state's or priority's `code`.** A CHECK cannot see a word in another table, so the naive fix (`code = 'blocked'`) would hardcode the very name the firm may rename, and the first rename would switch the rule off silently. `is_initial` / `is_terminal` / `is_blocked`, `is_default` / `is_statutory_default` / `rank` carry every rule; `enforce_work_item_state_facts` (a trigger) reads the flags. **The smoke walk renames "Blocked" to "Stuck" and proves the reason is still demanded.**
- **"At most one" is a partial unique index; "at least one" is the service** (`WorkVocabularyService`; Postgres cannot constrain the ABSENCE of rows): a firm with no starting state, default priority or statutory default cannot create a task. Marking another row moves the flag in the SAME statement.
- **`is_statutory_default`** is the firm's rule made mechanical ("due dates that are statutory should anyway be high priority"); a flag not the constant `'high'`. **Work spawned from an ENGAGEMENT is deliberately NOT statutory** (an SLA is the firm's own promise; defaulting true would make the flag meaningless); T3.2's obligations set it, from the law.
- **`slaDays` is PINNED and the Dept is LIVE on the same row.** A catalogue revision must not make finished work retroactively late (G2.3): SLA snapshotted from the signed version. The Dept comes from what is published NOW (the same rule `unspawnedActivations` applies to grouping facts; **the two must not drift** or a job cut by one Dept puts its task on another's desk). The due date's base is `crm.engagement.effective_from` (a `date`), never `signed_at`.
- **A SECOND approval table, the RULE not duplicated.** `work_item_approval` exists because `step_approval` hangs off a `job_step` and work with no template could never be reviewed ("every task is mostly reviewed", the client's words). Reused unchanged: T2.9's `isEligible`, `VerificationPolicy`, grade/reporting-line comparison. `submitted_by` is DERIVED from the item's assignee and FROZEN by trigger; **do not add a `submittedBy` to any write path.**
- **A task raised by hand is HIDDEN from the client unless the caller says (V1.4, 2026-09-28)**: `input.isClientVisible ?? false` (an internal note reached the portal). `spawnForEngagements` and `raiseForObligation` set `true` themselves. The column's DB default is still `TRUE` (0051); every insert names the value.
- **The reads My day is built from carry the client by ID and the due day (V2.1, 2026-09-28)** (six reads, no per-row lookup): `JobDetail` (`describeJobs`) gained `clientPartyId`, `entityPartyId`, `periodLabel`, `dueOn` (EARLIEST due day of the job's UNFINISHED tasks, `::text`); the orchestrator handler takes the scheduler as `deps.jobs` and puts it on `MyStep.job` and `StepCheck.job` (null when no engagement); `WorkItemCheck` gained `clientPartyId`, `dueOn` (queue row only); `EscalationRecord` gained `clientPartyId` (null on a filing). `tests/workitem/my-day-reads.integration.test.ts`.
- **A dependency is enforced on STARTING, never on finishing**; cancelling stays allowed (it would trap the item). The cycle check walks the edge list in the domain (reachability is not a CHECK; the DB catches only the self-edge).
- **`escalated_level` / `escalated_at` are deliberately NOT built** (T4.5 did not add them): the ladder keeps its own rows in `delivery.escalation_notice` (a level on the item loses when, which rung, whether anyone was reached, and a second reason).
- **Found by this task:** (1) `sweepActivations` promised per-tenant isolation but one firm's throw (a firm with no work vocabulary) skipped every later firm silently; each firm is caught and REPORTED (`SweepReport.failure`, printed by `worker:once`). (2) **A work-item failure must never lose the JOB** (job = work is OWED, task = whose desk): `spawnForEngagements` is caught inside the sweep and counted `tasksFailed`. (3) **PATCH was missing from the CORS allowlist** since CORS was added; the browser discards the request ("TypeError: Failed to fetch"); `npm run smoke` could not catch it (curl does not preflight); `tests/api/cors-methods.test.ts`. (4) A comment in 0051 was wrong until the integration test ran: a BEFORE INSERT trigger runs AHEAD of constraint validation, so the state trigger catches a cross-tenant state before the composite FK (both defences real; the trigger is the outer).

## The review loop, checklist, notes and filings (audit 2026-10-03, work cluster, 0330)

The roleplay walked a task from an article's desk to a manager's approval and found the loop open at both ends.

- **Approving FINISHES the task (CA#28).** `decideReview` → `followDecision` moves an approved task to `completedState` (active, terminal AND `isSuccess`, first by the firm's order) through the same `move` a hand move takes, so `completedAt`, `work_item.completed` and the calendar's `reconcileFiling` follow. A send-back moves a task in the firm's "with a checker" state to `reworkState` (active, not initial/terminal/blocked/under review: the seed's In Progress). A finished or cancelled task is never moved by a decision; a firm with no such state keeps the old behaviour. `work_item.state_changed` carries `byReviewDecision`. (`isSuccess`, 0054, tells Completed from Cancelled.)
- **The checklist is a gate (CA#30)**: `requestReview`, a move INTO a successful terminal state, and Approve refuse `CHECKLIST_OPEN` (409) naming open lines (`openChecklistLines`). Cancelling and Send back are never held. A line that does not apply is removed.
- **A task is checked under the FIRM's rule (CA#27).** A task names no rule, and absent meant maker != checker alone (an Analyst approved another Analyst's GSTR-3B). Now absent = the firm's ONE published rule (`ReviewPolicySource.publishedPolicies`), pinned as before; several = `REVIEW_RULE_NEEDED` (400) naming them; none = maker != checker alone. `GET /api/v1/review-rules` (`party:read`). **WAITS FOR SID:** with two rules (manager review and EQCR), should ad-hoc work default to one?
- **A task sent for review is no longer "Not Started" (F28)**: with no "with a checker" state flagged (0073's default), a task still in its STARTING state moves to `reworkState`. 0073's promise not to read "Under Review" as a mechanism stands.
- **Notes (0330).** `delivery.work_item_note`: one person's sentence at one moment, APPEND-ONLY (SELECT + INSERT; UPDATE and DELETE revoked), RLS, composite key, not blank by 0308's definition, <= 2,000 chars. `POST /work-items/{id}/notes` (`work:write`); the detail read carries `notes` oldest first with names. `work_item_approval.request_note` is what the maker says when sending (`requestReview` `note`). Ledger `work_item.note_added` with the note's id ONLY. Notes live on the items repository (`addNote` / `listNotes`).
- **Sent back shows on the maker's desk (CA#29)**: board row `sentBack` (`{ notes, decidedAt, decidedByName }`) when the latest DECIDED review was a send-back, none open, task not finished (lateral on `RECORD_SELECT`); `/my-steps` rows carry the same (`StepApprovalRepository.sentBackFor`, one `DISTINCT ON` per desk).
- **A task raised by hand can file a filing (CA#36).** `obligation_instance.work_item_id` already existed. `PUT /work-items/{id}/filing { obligationId }` (`ObligationService.linkWorkItem`; refused in words for another company's filing, one filed/withdrawn/decided/with its own task, a task already filing another); completing it files via `reconcileFiling` (a task already done files at once; the raise pass raises no second task). `DELETE` unlinks while unfiled; `GET` lists the linked filing and the company's open ones. Ledger `obligation.work_linked` / `obligation.work_unlinked`. The `ObligationFiling` port is built once for both processes in `setup/filing-link.ts`. **A process JOB finishing still files nothing by itself**; whether finishing the GST job should file GSTR-1/GSTR-3B is a design question with Sid, not built.
- `WorkItemCheckRow` carries `entityPartyId` / `entityName` (F32). Tests: `tests/workitem/{service,model,notes.integration,review-rules.integration,my-day-reads.integration}`, `tests/obligation/{service,task-link.integration}`, `tests/verification/queue.test.ts`.

## Work always has an owner: the owner rule (Shrestha, 2026-09-27, 0311)

Work the ENGINE creates (an engagement's task, a month's task, a filing's task, a job's steps) is never left on nobody's desk if somebody can hold it. `resolveOwner` in `domain/workitem/model.ts` is the one statement of the ladder:

1. the client's SPOC for the work's Dept (`resolveAssignee`, turn-taking), no note;
2. no SPOC: the client's **Key Manager**, to HAND OUT, with a note saying why;
3. no Key Manager: the **person who signs for the firm** (`/admin/firm`), same;
4. nobody: unassigned, the note naming all three gaps.

(Until 2026-09-27 rungs 2-3 did not exist, on the ground that a wrong assignee is worse than none; answered by the note: a fallback owner is TOLD on the row that it came to them to hand out.) A task raised BY HAND with nobody picked stays unassigned. **Only ACTIVE staff are candidates on any rung** (`infrastructure/postgres/work-owner.ts`; an assignment row outlives the membership it names). A Key Manager must be in force on the day (STARTED as well as not ended; `listOpenForClient` does not check the start and is not used).

- **MORE THAN ONE SPOC TAKES TURNS (Shrestha, 2026-09-25).** `SpocCandidate.routed` counts how many of THIS client's tasks the router has put on each desk; `resolveAssignee` picks the fewest; tie-break the longer-standing assignment. Nothing is stored (counter read off `delivery.work_item` each time, so a SPOC back from leave catches up). A job's steps follow the same rule through `PostgresJobDeskResolver`. (Before 2026-09-27 this was false for every firm on the default split: the resolver found the SPOC only via the job's split code, which a kept-together job lacks.)
- **The TASK and the job's STEPS call the same function.** `PostgresJobDeskResolver` found the SPOC through the split code only, so on split `none` every job's steps went to nobody while its task went to the SPOC (0 of 619 steps assigned locally; 30 of 30 on Dept-split jobs; nothing tested the file). The job's Dept is the split code when there is one, else the Dept of the job's services (LIVE): one = that Dept, several = `several_depts` (steps go to the Key Manager), none = a service filed under no Dept. `tests/orchestrator/owner.integration.test.ts` was watched red with the old behaviour and with the active-staff filter removed.
- **STEPS GO FIRST TO WHOEVER ALREADY HOLDS THE JOB'S TASK** (`StepOwnerFacts.taskHolder`: the one active staff member every open task of the job is on). A month's task is created at the period's START, the steps when it becomes runnable at the period's END; a Key Manager who handed the task out in between decided who does the month. Recorded `with_task` unless the ladder would name the same person. (Found by walking it.)
- **A fallback owner holds the TASK, not necessarily the steps** (a band decides who may hold a step). So **handing the task on hands out the job**: `WorkItemService.assign` → `JobStepHandover` → `OrchestratorService.adoptUnheldSteps`: every human step not settled and held by nobody or by the task's previous owner moves to the new owner wherever the band admits them (`job.step_assigned` `how: "with_task"`), only when every open task of the job is then on that desk; a step a colleague took stays theirs. The assign route answers `stepsHandedOver`.
- **0311 dropped `work_item_note_only_when_unassigned`** (0051 refused a note beside a name as stale; a fallback owner's note is the only thing telling them it is theirs to hand out; a hand move writes NULL over it, `setAssignee`). Its down REFUSES while any assigned task carries a note.
- **The owner is asked for on the FIRM's TODAY, the day the work is created** (`WorkItemService` holds a `timeZones` port), for a spawned task as for the steps. It used to be the engagement's `effective_from`, which split a task and its steps onto different desks whenever the team was named after that day (the book import does it every time; a handover sent November's task to September's SPOC). A SPOC named from a later day is still not today's. A filing's task (`raiseForObligation`) still asks on its due date.
- `how` on `work_item.assigned` and `job.step_assigned` names the rung (`spoc`, `key_manager`, `partner`).

### The catch-up: naming the account team moves the work waiting for it (2026-09-27)

The engine asks who owns a task ONCE, and the import names the team AFTER the paper letter, so naming the SPOC moved nothing. `ClientAssignmentService.assign` calls a `ClientWorkCatchUp` port after the assignment and its event (satisfied in `setup/server.ts` with `WorkItemService.catchUpClient`) and the route answers `caughtUp: { moves: [{ userId, tasks, steps }] }`, `null` when moving failed. **The assignment stands either way**; the failure is logged at `error` where the port is wired.

- **WHAT MOVES is only work nobody has decided about** (`listCatchUpCandidates`): the client's ENGINE work (engagement task, or a filing's through `obligation_instance`; never a hand-raised task), in a STARTING state, carrying a note that is not `TAKEN_OFF_BY_HAND_NOTE` (the sentence `assign` leaves when a PERSON takes a task off a desk): on the Key Manager's or signing partner's desk to hand out, or on nobody's with the router's sentence. **A task the SPOC holds carries no note and is never re-dealt**: naming a second SPOC, or a new one after a handover, moves none of the old SPOC's work. **A new Key Manager takes over the outgoing one's hand-out tasks** (Shrestha, 2026-09-27).
- Each candidate is asked `routeOwner` again on the day its creator asked (the firm's today; a filing's due date while ahead, else today). `catchUpMove` (domain): nobody = NOTHING (never taken off a desk); somebody else = a MOVE with that rung's note (none for a SPOC); same person by another rung = the desk stays and only the sentence changes, no event. The write `reroute` is refused by its own WHERE when holder, note (NULL-safe) or starting state changed since the read. Steps follow as on a hand move (`adoptUnheldSteps` from the one previous desk). Ledger `work_item.assigned` with the rung's `how` + `catchUp: true` + `fromUserId`, actor whoever named the team.
- **Not built:** nothing moves on the day a FUTURE-dated SPOC starts (no sweep); ENDING an assignment triggers nothing. `tests/workitem/catch-up.integration.test.ts` (seven clauses, each watched red when removed).

### The Send warning: where an unsigned letter's work will land (2026-09-27)

`GET /api/v1/engagement-letters/{letterId}/routing` (`party:read`): one row per Dept the letter's lines are filed under, whose desk the work would land on TODAY: `how` (rung or null), `ownerName`, `reason` (`no_spoc` · `no_dept` · `unknown_dept`, null when a SPOC takes it). It is the router's own question (`WorkItemService.routingForLetter` calls `routeOwner` over `LetterWorkSource`: client = the letter's party, Dept = the LIVE published service's `module`); a preview that joined differently would promise one desk and deliver another. A **warning, never a refusal** (decided 2026-09-27); the book import never sees it.

## Who may check somebody else's work (T2.9)

- **MAKER != CHECKER is the product's, not a setting.** `step_approval_maker_is_not_checker` (0048) (*a rule in a form is a rule a script, import or AI agent walks past*). `isEligible` applies it too, so a person is TOLD rather than shown a constraint violation. `maker-checker.integration.test.ts` proves it as the OWNER role.
- **`submitted_by` IS DERIVED AND FROZEN** (BEFORE INSERT reads it from `job_step.performed_by`; BEFORE UPDATE refuses to move it): otherwise a writer could name somebody else as maker and approve as themselves. **Do not add a `submittedBy` to any write path.**
- **WHO ELSE may check is the firm's: `verification_policy`, the registry's EIGHTH kind.** The client gave two answers on different days, two different controls: *"Manager or above is fine"* (rank threshold) and *"manager means engagement manager"* (reporting line, which stalls when that person is on leave). The demo's S3: *"the maker-checker control and not a line to draw on the firm's behalf"*. Rules: `rank_threshold` · `reporting_line` · `reporting_line_or_rank` · `client_key_manager` (Q069). **Nothing is seeded.** A kind, not a column (*who was allowed to approve this filing in March?*; an approval PINS the version it opened under). `minGradeRank` stores the RANK, not the code (a stored code would re-resolve against today's ladder).
- **A firm publishes SEVERAL; a step names one.** SQC 1 (ICAI quality control) wants an EQCR both suitably qualified (rank) and independent of the engagement team (the opposite of a reporting line). `excludeEngagementTeam` is deliberately NOT built ("engagement team" is the unsettled Dept-vs-delivery-team axis, G2.4; a rule on a guessed axis would decide who signs off an audit).
- **`membership.reports_to_user_id` is a FOURTH axis and grants nothing** (role = what you may reach, commercial visibility = money, grade = seniority, this = who checks your work under a reporting-line rule). Nothing else records a staff reporting line (`core.party_relationship` is between PARTIES). **Not effective-dated** (answers "now"; the ledger answers "when did it change"). Two refusals a database cannot make are the service's: a manager who is not an active STAFF member of this firm (the FK points at a GLOBAL table), and a loop (a CHECK cannot see past one row; it would leave everybody in it with no eligible checker).
- **A checked step does NOT finish.** It stays `blocked` (a fourth cause of that state; the work is DONE there), `performed_by` recorded, an approval opens. Approving finishes the step and advances the job in the same call; **rejecting moves nothing**, keeps the reason, and the redo opens a SECOND row ("this took two goes" survives).
- **`work:write` is a FLOOR under the firm's rule**: without it a read-only Management membership with a Senior Manager grade would pass a rank threshold (the demo's Q41, unanswered).
- **T2.9 lives on `OrchestratorService`** (a check is part of a STEP's lifecycle; opening a check happens when work finishes and vice versa); the RULE is pure in `domain/verification`.
- **The queue is the WHOLE FIRM's; every row carries the viewer's verdict**, oldest-first, no due date anywhere (the firm has not given turnaround times, client ask 3.4, or its escalation matrix, 3.3; an invented deadline is a priority the firm never set). `slaDays` stays earmarked for T3.1.

### Q069: the client's Key Manager checks the work (S8, 2026-10-05)

Ashish: "Client's engagement manager" (Shrestha read it as the Key Manager). A fourth `verification_policy` rule, `client_key_manager`: the ONE person who may check is the work's client's Key Manager in force on the firm's today, or, when there is none or they are the maker, the person who signs for the firm (the owner rule's last two rungs: `WorkOwnerDirectory` / `StepDeskResolver.ownerFactsFor`). `isEligible` takes the facts as a fourth argument (`ClientCheckers`), read ONLY under this rule; without them nobody qualifies (`NO_CLIENT_CHECKER`), never "anybody". Refusal `NOT_THE_CLIENTS_CHECKER`. Maker != checker and `work:write` still come first. The check notification follows `isEligible`. Nothing seeded: a firm publishes a rule with it (the rule form offers it first). Tests `tests/verification/eligibility.test.ts`.
